--------------------------------------------------------------------------------
## 1. 项目背景
--------------------------------------------------------------------------------

这是一个全新项目，灵感来自已归档的 Sakura-AI（一个 GitHub Issue/PR 的 AI 审查
机器人），但不是它的分支或重构。用户不是 Sakura 的开发者。

新项目要解决 Sakura 用户反馈的实际问题：

  用户反馈                    本项目的应对
  ------------------------    ----------------------------------------
  模型报错就整体失败          多模型故障转移（已实现）
  重复 Issue 检测误判         向量只做召回，不直接判定重复
  评级标准不合理              Severity 与 Priority 分离，
                              高等级必须有证据（已实现）
  一个 Issue 触发多次分析     dedupe_key + delivery 双层幂等（已实现）
  WebUI 太复杂                推迟到后端数据模型稳定后再做


--------------------------------------------------------------------------------
## 2. 技术栈与硬约束
--------------------------------------------------------------------------------

- Node.js >= 22，TypeScript strict
  （含 noUncheckedIndexedAccess、exactOptionalPropertyTypes、verbatimModuleSyntax）
- npm workspaces（不是 pnpm —— SMB 路径上 pnpm 符号链接会失败）
- Drizzle ORM + PostgreSQL 16（pgvector 镜像）、ioredis、Zod、Pino、Vitest
- API 使用 Node 原生 HTTP，无框架

禁止事项：

- 不使用 FastAPI/Python（用户明确拒绝）
- 不做 Telegram Bot（已从范围移除）
- API handler 内不得调用 AI、索引、Git clone 或任何长任务
- 应用启动时不得隐式执行 DDL 或修改 schema
- 不在 AI 或 GitHub 网络调用期间持有数据库事务
- 不把 GitHub token、Provider 凭据、Authorization、cookie、完整私有仓库内容
  或敏感 prompt 写入日志、任务事件或数据库 payload
- 不提交 .env、密码、密钥
- 只有 task-engine 可以修改任务状态；Worker 禁止直接 UPDATE analysis_tasks

重要的架构约束（易踩坑）：

跨包导入目前使用深层相对路径，例如：

    import { ... } from "../../../packages/domain/src/index.js";

这违反 M0 文档写的「禁止跨包深层导入」，但是有意为之的权宜之计：SMB 上
node_modules/@apertureprism/* 符号链接创建失败，所以包名导入无法解析。
沿用现有模式，不要擅自改成包名导入 —— 会直接构建失败。

## 3. 已完成的阶段
--------------------------------------------------------------------------------

### M0-M1：工程基线与基础设施

- monorepo、TS 配置、ESLint、Prettier、Vitest
- packages/config：Zod 环境解析，返回冻结对象
- packages/database：Drizzle schema、客户端、健康检查
- packages/observability：Pino + 敏感字段 redaction + correlation ID
- apps/api：/health/live、/health/ready

### M2：GitHub Webhook 接入

packages/github-adapter/src/index.ts：

- verifyWebhookSignature：对原始 body 做 HMAC-SHA256 + timingSafeEqual，
  在 JSON 解析之前
- normalizeGitHubEvent：规范化 issues / issue_comment / pull_request / ping，
  不泄漏 GitHub 结构到领域层

HTTP 语义：首次 202、重复 200、未配置 secret 503、签名错误 401、
缺 header 400、非法 JSON 400、非 POST 405。

### M3：持久任务引擎（packages/task-engine/src/index.ts）

状态机（只有这里能改任务状态）：

    queued -> leased -> running -> publishing -> completed
                          |            |
                      retry_wait -> queued
                          |
                        failed
    非终态 -> canceled

已实现函数：createAnalysisTask、createAnalysisTaskInTransaction、claimTask、
heartbeatTask、recoverExpiredLeases、startTask、beginPublishing、completeTask、
failTask、cancelTask、releaseDueRetries。

关键设计：

- 领取用 FOR UPDATE SKIP LOCKED，
  排序 priority desc, next_attempt_at asc, created_at asc
- completeTask 只能从 publishing 进入，不能从 running 直接完成
- publishing 阶段仍持有租约，支持心跳、过期回收和失败重试，
  避免发布中租约到期后永久卡死
- 取消会清租约、关闭未完成 attempt（errorCategory = "canceled"）、
  写 task.canceled 事件；终态任务拒绝取消
- 幂等键：
    issue-analysis:{repoUuid}:{issueNumber}:{updatedAt}:{policyVersion}
    pr-review:{repoUuid}:{prNumber}:{headSha}:{policyVersion}

踩坑记录：Drizzle 原始 SQL 中不能直接传 JS Date（postgres-js 会抛
ERR_INVALID_ARG_TYPE）。必须写 ${date.toISOString()}::timestamptz。
typed .set() 可以正常传 Date。

### M4a：Webhook -> 任务持久化

packages/database/src/webhooks.ts 的 ingestGitHubWebhook 在单个事务内完成：
delivery 幂等插入 -> 仓库 upsert -> 任务 create-or-get -> 标记 delivery 结果。
任一步失败整体回滚，保留 GitHub 重投能力。

触发规则：issues 仅 opened/edited/reopened，
pull_request 仅 opened/reopened/synchronize。
issue_comment 当前标记 ignored 不建任务（命令解析和权限校验未实现）。

### M4b：多模型路由器

packages/model-router/src/index.ts：

- routeModelInvocation：统一 logical deadline 覆盖所有候选、重试和 backoff，
  不按候选重置
- 认证失败 / 模型不存在 / 上下文超限 -> 不在同一候选重试，直接换候选
- 任务内候选粘性：优先已成功的模型，同时保留全部 fallback
- 尊重 Retry-After，否则指数退避
- AbortSignal 双向传播

packages/model-router/src/openai-compatible.ts：基于 fetch，只做翻译和错误映射，
不决定重试。400 需查响应体才能区分上下文超限。

packages/config/src/credentials.ts：AES-256-GCM 封装凭据，随机 IV，
认证标签防篡改，版本前缀 v1 预留轮换。解密失败统一抛 CredentialEncryptionError，
不透出底层 cipher 错误。

### M5a：结果契约与 Worker 循环

packages/contracts/src/issue-analysis.ts、grading.ts：

- Severity（S0-S3/unknown）与 Priority（P0-P3/needs_triage）独立，不合并
- 降级逻辑在服务端，不指望提示词约束模型
- impact_scope 不算实质证据 —— 模型能凭空断言「影响所有用户」，
  但造不出堆栈或日志
- .strict() schema，未知字段直接拒绝
- 每次降级记录 from / to / reason

apps/analysis-worker/src/loop.ts：

- task-engine 操作全部注入，循环从不自己 UPDATE
- 心跳失败即中止 handler，防止两个 Worker 为同一 attempt 重复发布
- 关机时取消在途 handler 并显式记为 canceled
- 当前 handler 返回 analysis_not_implemented，如实反映未实现而非假装成功

--------------------------------------------------------------------------------

按顺序完成 M5 剩余部分，把分析逻辑接进 Worker handler：

1. Issue 上下文构建（packages/issue-analysis/，目前是空占位）

   - 提示词带版本号，纳入 policyVersion 以便幂等键随策略变化

   - 上下文 -> routeModelInvocation -> parseIssueAnalysisJson
     -> applyGradingRules

   - attempt 的 token / 耗时落库

4. GitHub 幂等评论发布
   - 用 external_publications 表的 idempotency_key，重试不产生重复评论
   - 占位评论 + 原位更新
   - 第一版不自动关闭 Issue

之后是 M6 重复检测、M7 PR Review、M8 WebUI + SSE。

## 6. 工作方式期望
--------------------------------------------------------------------------------

- 一次一个阶段，纵向切完再进下一个，不要同时铺开多个模块
- 不要用 mock 掩盖真实问题。集成测试失败就报告具体的数据库/网络原因，
  不要跳过或伪造通过
- 测试失败先判断是代码 bug 还是测试假设错误，两者都发生过：
    * Worker 预中止竞态是真 bug
      （signal 已中止时 { once: true } 监听器永不触发）
    * API 启动超时是测试预算不符现实（SMB 冷启动 23.5 秒 vs 25 秒预算）
- 未实现就如实标记，不要让占位实现看起来像能用
- 提交前询问用户；不要主动 push
